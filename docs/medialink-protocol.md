# MediaLink WebSocket 协议

> 本文档是面向客户端开发者的独立参考。实现一个基本客户端只需 WebSocket 支持和本文档。

## 概述

MediaLink 是 ClassIsland 媒体信息插件提供的本地 WebSocket 推送服务。客户端通过 `ws://` 连接，经过认证与订阅后，即可接收当前播放的媒体信息和逐字歌词。

- **传输**: 明文 `ws://`（无 TLS）
- **默认地址**: `ws://127.0.0.1:21757/v1/ws`
- **协议版本**: `v: 1`（仅追加，不破坏已有客户端）
- **认证**: Token（base64url 字符串，在 ClassIsland 设置页生成）

## 连接

### WebSocket 握手

标准 WebSocket 握手，路径为 `/v1/ws`。支持 query 参数（如 `/v1/ws?foo=1`）。

服务端校验以下请求头（全部不通过则拒绝连接）:

| 请求头 | 要求 | 拒绝时状态码 |
|--------|------|-------------|
| 路径 | 精确为 `/v1/ws`（允许 query） | 404 |
| `Connection` | 包含 `Upgrade` | 400 |
| `Upgrade` | `websocket` | 400 |
| `Sec-WebSocket-Version` | `13` | 426 |
| `Sec-WebSocket-Key` | 存在且为 16 字节 base64 | 400 |
| `Host` | 匹配监听地址 / localhost / 127.0.0.1 | 403 |
| `Origin`（可选） | 在允许白名单内 | 403 |

### 握手超时

服务端等待完整请求头的时间上限为 **5 秒**，超时则断开。

## 信封格式

所有消息（客户端→服务端和服务端→客户端）使用统一 JSON 信封:

```json
{
  "v": 1,
  "type": "消息类型",
  "id": "请求ID（可选）",
  "ts": 1710000000000,
  "seq": 42,
  "name": "事件名（仅 event 类型）",
  "payload": { ... }
}
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `v` | int | 是 | 协议版本，当前为 1 |
| `type` | string | 是 | 消息类型（见下文） |
| `id` | string | 否 | 请求-响应关联 ID |
| `ts` | long | 是 | Unix 毫秒时间戳 |
| `seq` | long | 否 | 单调递增序号（默认 0 时不发送） |
| `name` | string | 否 | 事件类型名（仅 `type=event` 时存在） |
| `payload` | object | 否 | 消息载荷 |

> **必须容忍**未知字段和未知枚举值，忽略即可。

## 消息类型

### 认证

#### `auth`（客户端→服务端）

连接后 10 秒内必须发送，否则被强制断开。

```json
{
  "type": "auth",
  "id": "a1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "token": "你的Token字符串"
  }
}
```

服务端响应:

- `auth_ok` — 认证成功
- `auth_fail` — Token 错误，随后断开连接
- `error` + `unauthorized` — 未认证即发送业务消息

#### 认证失败限速

同一 IP 认证失败 **5 次/60 秒**后，新 TCP 连接将被立即关闭。

### 订阅

#### `subscribe`（客户端→服务端）

```json
{
  "type": "subscribe",
  "id": "s1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "channels": ["media", "lyrics"]
  }
}
```

可用频道:

| 频道 | 说明 |
|------|------|
| `media` | 媒体信息变更事件 |
| `lyrics` | 歌词搜索结果事件 |
| `audio` | PCM 音频帧（二进制，见「音频」一节） |

服务端响应 `subscribe_ok`，随后推送快照（当前状态）和增量事件。

> `subscribe` 的语义是**整体替换**而非追加：服务端以本次请求的 `channels` 取代原有订阅集合。
> 因此追加一个频道时必须把已订阅的频道一并带上，只发新增的那一个会把其余频道顶掉。
> 需要精确移除某个频道时用 `unsubscribe`。

#### `unsubscribe`（客户端→服务端）

退订部分频道:

```json
{
  "type": "unsubscribe",
  "id": "u1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "channels": ["lyrics"]
  }
}
```

服务端响应 `unsubscribe_ok`，携带已移除的频道列表。退订未订阅的频道会返回 `error` + `bad_request`。

### 心跳

#### `ping` / `pong`

```json
{"type": "ping", "id": "p1", "v": 1, "ts": 1710000000000}
```

服务端回复 `pong`，携带相同的 `id`。

### 回程对时

#### `audio.clock`（客户端→服务端，服务端应答）

四时间戳回程对时，供接收端估计自己与发送端单调时钟之间的偏移（offset），
是跨机播放对齐的基础。需先认证；不要求订阅任何频道。仅当 `server.hello` 的
`capabilities` 含 `audio.clock` 时才应发送（见「server.hello」一节）。

请求只带 `t1`（客户端发出时刻）:

```json
{
  "type": "audio.clock",
  "id": "c1",
  "v": 1,
  "ts": 1710000000000,
  "payload": { "t1": 123456789012345 }
}
```

服务端应答复用同一个类型名 `audio.clock`，携带相同的 `id`，载荷带 `for`——
与 `thumbnail` 一样是「请求换一份数据」而非「请求换一个确认」，故不走 `ok`:

```json
{
  "type": "audio.clock",
  "id": "c1",
  "v": 1,
  "ts": 1710000000123,
  "payload": {
    "for": "audio.clock",
    "t1": 123456789012345,
    "t2": 987654321098765,
    "t3": 987654321101234
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `for` | string | 仅应答携带，恒为 `audio.clock`——与 `ok` 的 `payload.for` 同形，标记「这是对哪类请求的应答」 |
| `t1` | i64 | 客户端发出请求的时刻（客户端单调时钟）；应答中原样回显 |
| `t2` | i64 | 服务端收到请求的时刻（服务端单调时钟），取在解析 JSON 之前 |
| `t3` | i64 | 服务端发出应答的时刻（服务端单调时钟），取在拿到发送权之后 |

t4（客户端收到应答的时刻）由客户端自己取，不在报文里。

请求缺 `t1` 时服务端回 `error` + `bad_request`，而不是回一个 `t1` 为 0 的应答——
后者会让客户端算出一个巨大的 offset 并当真。

#### 为什么不复用 `ping`

`ping` / `pong` 只能给出三个时刻：请求发出（t1）、应答发出（t3）、应答收到（t4）。
缺了 **t2（服务端收到请求的时刻）**，就必须假设服务端从收到到发出的处理耗时为零——
而服务端一次 GC 或一次锁竞争就是几十毫秒，那段时间会被算进网络往返，同时污染
offset 与它的可信度估计，且不留任何痕迹。四时刻里 t2→t3 这段服务端内部耗时是
被显式测出并从往返中剔除的，这正是新消息存在的理由。

（此外 `pong` 根本不携带单调时钟读数，信封 `ts` 是墙钟且只有毫秒精度——
即便接受三时刻假设，它也不是能用的载体。）

#### 单位与时钟

- `t1`–`t4` 一律为 **i64，单位 100 纳秒 tick**：1 毫秒 = 10⁴ tick，1 秒 = 10⁷ tick。
  该刻度与 .NET 的 `TimeSpan.Ticks` 及 WASAPI 的 QPC 位置字段一一对应，两侧都不需要
  换算代码。不用毫秒是因为 offset 估计的误差本身只有 0.5 毫秒量级，毫秒量化会污染它。
- 四个时刻都必须取自**单调时钟**（Windows 上即 QPC 类，如 `Stopwatch`；浏览器
  `performance.now()` 换算；Python `time.monotonic_ns() // 100`）。**墙钟不参与**：
  offset 要跨分钟级持续维持，而墙钟会被 NTP slew 或 step 调整，一次调整就让此前
  所有样本失效且无从察觉。
- 单调时钟的零点不是日历时刻（通常是系统启动），只可用于求差；t1/t4 与 t2/t3
  分属两台机器的时钟，零点不同，这正是要估 offset 的原因。
- **信封的 `ts` 是 Unix 毫秒墙钟**（见「信封格式」一节），与 `t1`–`t4` 不是同一个
  时钟——零点不同、刻度不同、受 NTP 调整。**不得拿 `ts` 参与 offset 计算**；
  它在对时里唯一的用途是与同一条应答里的 `t3` 配对作墙钟桥（见下文）。

#### 时刻的取点义务

四时刻的价值取决于每个点取在哪里，取错位置不报错、只污染结果，故取点是协议义务
而不是实现细节：

- **服务端：`t2` 取在解析 JSON 之前。** 解析耗时随载荷大小与 GC 时机波动，取在
  解析之后它就被算进了「网络往返」。由于判断消息类型本身就要先解析，这意味着
  服务端要对每条入站消息都先打点再解析。
- **服务端：`t3` 取在拿到发送权之后。** 出站方向可能有锁或队列等待，取在等待之前
  这段耗时就混进了 t3→t4 的单程。这要求应答报文延迟构造——`t3` 只能在真正要写出
  的那一刻填。
- **服务端：应答信封的 `ts` 与载荷 `t3` 必须同瞬取得**（本仓实现：延迟构造的同一个
  工厂里相邻取值，相差微秒量级）。这一对是线上唯一同瞬的墙钟/单调钟读数，接收端的
  时钟轴合成（墙钟桥）完全依赖它——两者若在相隔可感的时刻取得，桥的误差直接进入
  出声时刻且无从察觉。
- **客户端（对称义务）：`t4` 取在收到应答字节处**，进任何分支与 JSON 解析之前；
  且 `t1` 与 `t4` 必须同源（同一个单调时钟）。

#### offset 与往返的计算

```
offset = ((t2 − t1) + (t3 − t4)) / 2    客户端时刻 + offset = 服务端时刻
rtt    = (t4 − t1) − (t3 − t2)          已剔除服务端处理耗时
```

- **rtt 物理上不可能为负。** 为负说明字段错位或对端时钟中途被重置，该样本要**丢弃**
  而不是夹紧到零——夹紧会让一个坏样本看起来像最好的那一个，而「最好的那一个」
  正是选择依据。
- **应答的 `t1` 必须与在途请求的 `t1` 比对**，不符即弃：迟到或重复的应答配上本次的
  t4，往返会算成两次探测的间隔——一个大得离谱又看起来合法的数。
- 在最近 **8 个样本**的窗口里**挑最小 rtt 那次**，不取平均：排队延迟只会让 rtt 变大，
  对 offset 的污染上界是 rtt/2，取最小者即取污染上界最小者；取平均则把所有样本的
  排队延迟都掺进结果。8 秒窗口内两台机器单调时钟的相互漂移只有约 0.08 毫秒，
  可当作常量偏移，故窗口内不需要估 skew。
- 最小 rtt 超过 **50 毫秒**时报「offset 不可用」，而不是照样给一个值：此时 offset
  误差可达 25 毫秒，已吃掉整个对齐误差预算，退回非对齐比假装对齐正确。

#### 探测节奏（本仓客户端实现，供参照）

- 快速阶段：**每 200 毫秒一次，直到累计接受 8 个样本**（约 1.6 秒填满窗口）。
  阶段按「已接受的样本数」而非「已发出的探测数」判断——样本没配成时窗口仍是空的，
  该继续密集探。
- 稳态：**每 1 秒一次**。1 秒周期配 8 样本窗口覆盖约 8 秒，见上文漂移论证。
- **连续 3 次无回应算失联**，清空整个窗口：留着旧样本会让上层在链路已断时继续按
  一个越来越旧的 offset 对齐，而它的误差没有上界。取 3 而非 1 是因为单次丢包在
  无线链路上是常态，一次丢包就清窗会让 offset 反复进出可用状态。**清窗后按空窗
  重新走快速阶段**——上文「阶段按已接受的样本数判断」的直接推论：清窗后窗口
  就是空的，该密集探而不是按稳态周期慢慢补。
- 计入这个连续计数的不只是超时无回应：**回显 `t1` 不符、样本被拒（负 rtt）也各算
  一次没成**。否则一个每次都回应、但回的样本恒不可用的对端（例如 t2 取自单调钟而
  t3 取自墙钟）永远到不了失联阈值，窗口里最后一次被接受的 offset 被无限期沿用，
  而没有任何计数说得出它已经很旧了。
- **断连即清空：样本窗口与「对端不支持」判定都要清，重连从空窗开始**（快速阶段
  重新走）。重连后的对端可以是另一台机器，旧样本描述的是它的单调时钟零点与本机
  的映射——那段关系已经不存在，跨重连沿用旧 offset 的误差没有上界。「对端不支持」
  同理指向的是旧对端，不清的话一旦连过一个只实现三时刻的对端，此后连到任何机器
  都不再对时，且归因指向错误的那一台。（注意清空的理由是**换了机器**，不是对端
  进程重启：单调时钟零点是系统级的，同一台机器上进程重启不改变它。）
- 单次应答的等待上限 1 秒；超时按无回应计。
- 应答缺 `t2` 或 `t3` 即对端只实现了三时间戳：判「对端不支持」，本条连接内不再探。
  不退化成三时刻估计——那会给出一个看起来可用的错值，比报不可用坏得多。

#### 墙钟桥与目标出声时刻

音频帧头的 `capturedAtMs` 在**发送端墙钟轴**（Unix 毫秒，见「帧格式」一节），而上文
的 offset 建立在两端**单调钟**之间。要把帧头时刻搬到本机单调钟轴，还差一座
「发送端墙钟 → 发送端单调钟」的桥，它只能来自应答里同瞬的（信封 `ts`，`t3`）一对：

```
W          = ts × 10⁴ − t3                发送端墙钟(换成 100ns) − 发送端单调钟
线上offset  = −offset − W                  本机单调钟 − 发送端墙钟(换成 100ns)
目标出声时刻 = capturedAtMs × 10⁴ + dMs × 10⁴ + 线上offset     （本机单调钟轴，100ns）
```

其中 `dMs` 是 `server.hello` 声明的播放延迟预算（见「server.hello」一节）。
W 取自**最近一次被接受样本**所在的那条应答，不做窗口平滑：W 在同一台对端上是
准常量，逐样本差异只有 `ts` 的毫秒量化 ±0.5ms。发送端墙钟被 NTP step 时 W 跳变，
但所有接收端共享同一个发送端墙钟，跳变对全体接收端共模，不破坏相对对齐。

本仓两个示例还在此式上叠加了手动出声偏移（正值推后出声），作为自动估计对不上
耳朵时的旁路；注意它与本仓产品实现的手动偏移（作用在实测出声侧：正值声明本设备
实际出声更晚，补偿后听感提前）**同名反向**——在示例与产品之间移植或对读时，
刻度要取反。

失联清窗（见「探测节奏」）**不必清桥**，这是惰性等价而非义务：清窗后合成被
「offset 不可用」挡住，桥值在下一个被接受样本到来之前不可能被消费，而那个样本
必然重写桥——清与不清从连接外部不可区分，实现随便选。断连清空（同节）则必须
把桥一并清掉：它与样本窗描述的是同一段已不存在的时钟映射。

两段刻意分开：offset 走四时刻的最小往返选择（0.5ms 量级），W 走同瞬对（±0.5ms
量化）。把墙钟直接混进 offset 估计会让 NTP 调整污染整窗——这也是上文「不得拿
`ts` 算 offset」的另一面。

#### 没对齐的原因与诊断路径

对齐随时可能不可用，四种原因的排查方向完全不同，实现必须可区分地归因——合成一条
「对齐不可用」的消息，用户就无从知道该去检查服务端版本、配置、网络、还是自己的设备：

| 原因 | 判定 | 诊断路径 |
|------|------|---------|
| 能力缺失 | `capabilities` 无 `audio.clock` | 服务端不支持跨机对时，升级或更换服务端 |
| 未声明预算 | 有能力，但 hello 无 `audioClock.dMs` | 发送端配置不全，查发送端的配置与版本 |
| 预算办不到 | `dMs` 超上界 10000ms；为 0、为负；或减去本机各段延迟后越出本实现可执行的深度区间——不足自身最小抖动缓冲深度，或装不进自身的积压上限。**具体数值由各实现自定**（本仓下界 50ms），义务只是判定不过就退回非对齐并把方向说出来 | 改发送端的 `dMs`（不足下界调大、超出上限调小），或换更快的本机设备 |
| offset 不可用 | 窗口空、最小 rtt 超 50ms、或失联清窗 | 等待自愈，或查网络 |

- 「未声明预算」与「预算办不到」是两回事：前者去查发送端版本与配置完整性，
  后者去改那个配置值。接收端**不得**在未声明时回落默认值（论证见「server.hello」
  一节的「消费 audioClock」）。
- 预算的**上界 10000 毫秒**不是性能参数，是防御：真实链路用不到 10 秒量级的预算，
  落在其外的数只可能是配置写错或单位错填（微秒、100ns 填进了毫秒字段）；且预算
  换算成 100ns tick 要乘 10⁴，不设上界时一个荒唐大的值可能溢出成负数目标，
  而它在下界那一关是绰绰有余的——上界把这条路堵在换算之前。
- 「装不进自身积压上限」与「不足最小深度」同属「预算办不到」，方向相反：深度
  超过实现的积压上限时，帧在等到目标出声时刻之前就会被「积压丢最旧」持续顶掉，
  闸门永远追不上被推进的头部——表象是**永久静音加持续丢帧**，而不是延迟偏大。
  在判定处退回非对齐并提示调小 `dMs`，比让积压边界静默顶穿对齐好归因得多。
- 判定顺序应当是：先协议层（能力、预算声明），再本机静态可行性（预算装不装得下），
  最后才是运行时状态（offset 可用性）。运行时状态是唯一会自己好转的一条，把它排在
  前面，一台预算根本不够的机器刚连上的几秒会报「还没对上时钟」——那条提示指向
  等待，用户就会一直等。
- 四种情形一律**退回非对齐播放**：不断连、不停止出声，`media` / `lyrics` / 转发
  三条数据通道不受影响。对时只服务于对齐，它不可用时播放退回本地缓冲深度控制。
- 运行时的退回不是单向门：offset 失而复得后，对齐要能重新进入——与 hello 重发
  「改回来要能重新进入」（见「消费 audioClock」）同一义务。重新进入的**时机**由
  实现自选：立即重排会打断正在出声的流（一次可听跳变），等下一次自然的锚点重排
  （欠载重排、缓冲重置）则零跳变、但恢复时刻不定。两个示例客户端都选后者，并在
  状态行把「在等什么」说出来——指向等待的文案，其实际条件必须真的是等待。

## 事件

### `media.updated`

媒体状态变更。`payload` 结构:

```json
{
  "changeKind": "MediaProperties",
  "sourceApp": "Spotify.exe",
  "title": "歌曲名",
  "artist": "歌手",
  "albumTitle": "专辑",
  "positionMs": 30000,
  "durationMs": 180000,
  "playbackState": "Playing",
  "playbackRate": 1.0,
  "hasThumbnail": true,
  "trackToken": "abc123def",
  "positionCapturedAtMs": 1710000030000,
  "serverTimeMs": 1710000030050
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `changeKind` | string | 变更类型：`CurrentSession` / `MediaProperties` / `Playback` / `Timeline` |
| `sourceApp` | string | 来源进程名 |
| `title` | string? | 歌曲名 |
| `artist` | string? | 歌手 |
| `albumTitle` | string? | 专辑名 |
| `positionMs` | long | 当前播放位置（毫秒） |
| `durationMs` | long | 总时长（毫秒） |
| `playbackState` | string | 播放状态：`Playing` / `Paused` / `Stopped` / `Opened` / `Changing` / `Closed` / `Unknown` |
| `playbackRate` | double? | 播放速率 |
| `hasThumbnail` | bool | 是否有封面（获取方式见缩略图端点） |
| `trackToken` | string | 曲目标识，同一曲目稳定不变，切歌时变化 |
| `positionCapturedAtMs` | long | 位置采样时刻（Unix 毫秒） |
| `serverTimeMs` | long | 消息发送时刻（Unix 毫秒） |

#### trackToken 的计算

`trackToken` 是四元组 `(sourceApp, title, artist, albumTitle)` 的 SHA-256 前 8 字节，
小写十六进制。四个字段以 U+001F 连接后入哈希——用不可打印分隔符是为了避免字段内容
拼接产生歧义。

**入哈希前先规范化**，否则两端对同一曲目会算出不同的 token，而接收端会把全部音频帧
判为过期曲目并静默丢弃：

- 每个字段去掉首尾空白，故 `" A "` 与 `"A"` 同值；
- 三个可选字段的 null、空串、纯空白三者同义，一律记为空串；
- `sourceApp` 为空或纯空白时记为 `external`。

**不做**的规范化同样是契约的一部分：大小写不折叠，字段内部的空白原样保留。
故 `"A B"`、`"a b"`、`"AB"` 是三个不同的 token。

规范化幂等，已清洗过的字段再传一次不改值。跨实现只要照此计算即可得到相同的 token。

#### 进度插值

服务端**不会**周期性推送位置。播放中位置由客户端本地插值得出，仅在
`playbackState` / `playbackRate` 变化或切歌时才有新的 `media.updated`。

客户端应使用三元组 `(positionMs, positionCapturedAtMs, serverTimeMs)` 插值：

```
若 playbackState == "Playing":
    位置 = positionMs
         + ((serverTimeMs - positionCapturedAtMs) + (本地当前时刻 - 本地收帧时刻))
           × playbackRate
否则:
    位置 = positionMs
```

两个差值各自在**同一个时钟内**求得，因此客户端不需要与服务端对时：

- `serverTimeMs - positionCapturedAtMs`：服务端内部从采样到发送的延迟，两值都出自服务端时钟。
- `本地当前时刻 - 本地收帧时刻`：客户端收到该帧后经过的时间，两值都出自客户端时钟。

> **不要**写成 `本地当前时刻 - serverTimeMs`。那是拿两台机器的时钟直接相减，
> 只在双方时钟严格同步时才成立；跨机消费（例如另一台设备上的歌词条）会得到
> 一个等于时钟偏差的固定误差。

本地时刻建议取单调时钟（浏览器 `performance.now()`、Python
`time.monotonic()`），避免系统时间被 NTP 校正时进度跳变。

结果应按 `[0, durationMs]` 截断。

JavaScript 参考实现：

```js
// 收到 media.updated 时：recvAt = performance.now()，并存下 payload
function positionNow(p, recvAt) {
  if (p.playbackState !== 'Playing') return p.positionMs;
  const elapsed = (p.serverTimeMs - p.positionCapturedAtMs)
                + (performance.now() - recvAt);
  const pos = p.positionMs + elapsed * (p.playbackRate || 1);
  return Math.min(Math.max(0, pos), p.durationMs || pos);
}
```

歌词搜索结果。`payload` 结构:

  "title": "歌曲名",
  "artist": "歌手",

### `server.hello`

连接后服务端自动发送:

```json
{
  "type": "event",
  "name": "server.hello",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "protocolVersion": 1,
    "authRequired": true,
    "sessionEpoch": 3,
    "capabilities": ["audio", "audio.clock"],
    "audio": { "sampleRate": 48000, "channels": 2, "format": "s16le" },
    "audioClock": { "dMs": 300 }
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `protocolVersion` | int | 服务端协议版本 |
| `authRequired` | bool | 是否需要认证 |
| `sessionEpoch` | long | 监听器实例代号，进程内单调递增 |
| `capabilities` | string[]? | 服务端支持的可选能力；缺失表示只支持基础频道 |
| `audio` | object? | 音频线格式；`capabilities` 含 `audio` 时存在 |
| `audioClock` | object? | 跨机播放对齐的参数声明；`capabilities` 含 `audio.clock` 时存在 |

`capabilities` 的已定义取值：

| 取值 | 含义 |
|------|------|
| `audio` | 支持 `audio` 频道与 `audio.play_start` / `audio.play_stop`（见「音频」一节） |
| `audio.clock` | 支持 `audio.clock` 回程对时（见「回程对时」一节）。能力名即它启用的那个消息名，少一层需要两边同时记住的映射 |

`audioClock` 的字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `dMs` | long? | 播放延迟预算，毫秒：每个采样应在「发送端采到它的时刻 + `dMs`」出声。由发送端配置（本仓实现默认 300），全体接收端共用同一个声明值。缺失时接收端按「不支持对齐」处理，**而不是取默认值** |

`sessionEpoch` 用于识别服务端重启：`seq` 在监听器重建后从 0 重新开始，客户端若一律「丢弃 seq ≤ 已处理值」会永久停止更新。正确做法是**发现 `sessionEpoch` 变化时重置已处理的 seq 水位**。

#### 消费 capabilities

`server.hello` 并非只在握手时出现一次：**同一条连接存活期间服务端可能再次发送**，
用于重新声明当前状态。每条 hello 都是一份完整声明，客户端应**以最新一条为准**
覆盖已记录的能力，而不是只在握手时记一次——否则中途的能力变化无从察觉。

缺 `capabilities` 字段的旧服务端应按空集合处理，即「不支持任何可选能力」。

> 订阅 `audio` 前应先检查 `capabilities` 是否含 `"audio"`。旧版服务端不认识该频道，
> 会以 `bad_request` 拒绝整个 `subscribe` 请求——包括其中的 `media` 与 `lyrics`。

#### 消费 audioClock

`dMs` 是**发送端的声明**，不是接收端的建议值：多台接收端要在同一空间同时出声，这个预算
必须全局一致，各接收端自己配一个不同的数就直接失败。故接收端一律照声明值执行。

`server.hello` 可在连接存活期间重发并改 `dMs`，接收端与 `capabilities` 一样**以最新一条
为准**：改小到本机办不到就退回非对齐，改回来要能重新进入。能力与 `dMs` 出自同一条 hello，
接收端应成组读取——分两次取回的两半可能来自两条 hello，那会让归因指错方向。

字段缺失——没有 `audioClock` 对象，或对象里没有 `dMs`——时，接收端**按「不支持对齐」处理，
不得回落到默认值**。回落会让两端各自默认成一个数：看起来一致，实际是两份各自为真的声明，
改了一端就静默失配，而症状是两台机器差一个固定的量、看着像硬件延迟。

「声明了一个办不到的值」与「没有声明」是两回事，接收端应分开归因：前者去改发送端的
配置值，后者去查发送端版本。`dMs` 为 0、为负、或大到本机无从执行都属前者。

`capabilities` 含 `audio.clock` 只表示协议支持，`dMs` 本机能不能满足是运行时的事——
与上面 `audio` 那条立场相同，两者报不同的原因，否则一次「预算配得太小」会让人以为
对端根本不懂这个协议。

### `media.inject`

```json
{
  "type": "media.inject",
  "id": "inj1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "sourceApp": "upstream-instance",
    "title": "歌曲名",
    "artist": "歌手",
    "albumTitle": "专辑",
    "positionMs": 30000,
    "durationMs": 180000,
    "playbackState": "Playing",
    "playbackRate": 1.0,
    "positionAgeMs": 120
  }
}
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `title` | string | 是 | 空白则 `bad_request` |
| `sourceApp` | string? | 否 | 省略时为 `external` |
| `positionMs` / `durationMs` | long | 否 | 必须 ≥ 0 |
| `playbackState` | string | 是 | 同 `media.updated` 的取值 |
| `playbackRate` | double? | 否 | 默认 1.0 |
| `positionAgeMs` | long? | 否 | `positionMs` 的采样距今已过去多少毫秒，默认 0 |

#### `positionAgeMs` 与转发

把本实例收到的 `media.updated` 转发给下游实例时，**必须**填 `positionAgeMs`，
否则每转发一跳，进度都会落后一次传输与处理的耗时。

用相对量而非绝对时间戳是刻意的：绝对值要求两台机器时钟同步，相对值只依赖
发送方自己的时钟差。计算方式与 §进度插值同源：

```
positionAgeMs = (serverTimeMs - positionCapturedAtMs) + (本地当前时刻 - 本地收帧时刻)
```

服务端会据此把时间基准回拨，使注入后的位置从采样那一刻算起继续推进。
`playbackState` 非 `Playing` 时该字段无效——暂停的曲目位置不随时间前进。

#### 实例间消费

MediaIsland 自带客户端实现，可直接消费另一台实例的推送：在设置页「消费其它实例」
中填入对方的地址与 Token 即可。收到的媒体与歌词写入本机的**外部注入**，因此还需
把「媒体源模式」设为「外部优先」或「仅外部注入」才会生效——保持「仅系统会话」时
数据会被收下但不参与合成。

推送与消费相互独立，一台实例可以只推、只收，或两者同时（即转发中继）。

**配置码**：设置页可把本机的「地址 + 密钥」打包成一串 `medialink:` 开头的文本，
在另一台设备一键粘贴导入，免去手抄 32 字节密钥。

> 配置码只是 base64url 编码的明文 JSON，**不是加密**。任何拿到它的人都能解出密钥，
> 只应发给信任的设备。之所以编码而非直接展示 JSON：避免用户漏抄花括号与引号，
> 也让「这是机密」在视觉上更明显。

歌词的 `source` 字段在转发时保留其**最初来源**（如 `QqMusic`）而非转发通道，
故多跳转发后仍能看出歌词实际来自哪里。


## 音频

音频帧不走 JSON 信封，使用 WebSocket **二进制帧**。一帧 10ms 的 PCM 约 1920 字节，
base64 进 JSON 会膨胀三分之一，且每帧都要过一遍序列化器。

订阅 `audio` 频道后开始接收。格式由 `server.hello` 的 `audio` 字段声明，当前恒为
48000Hz / 2 声道 / i16 小端交错。

### 帧长由设备决定，不是固定值

**帧长不是协议的一部分，也不由服务端选定。** 帧头不携带时长字段，`server.hello` 的
`audio` 声明也只有 `sampleRate` / `channels` / `format`，因此帧长无法从协议本身推导。

第 2 期真机实测：本仓服务端在 Windows WASAPI 共享模式下**每帧约 10ms**（PCM 部分
1920 字节，约 99 帧/秒）。这不是可配置项——共享模式下 `hnsBufferDuration` 只是最小
缓冲尺寸，实际包周期由音频引擎的设备周期决定，通常为 10ms。换一台设备、换一个平台，
该值都可能不同。

接收端**必须**按实际收到的 PCM 字节数计算本帧时长：

```
帧时长(ms) = PCM 字节数 / (sampleRate × channels × 每样本字节数) × 1000
```

把任何具体帧长写死在接收端，采集设备一变，缓冲时长就会静默漂移而不报错。

> 早期草案曾把「每帧 20ms」写成约定，实测证明服务端做不到这一保证。
> 下文提到的队列时长换算按 10ms/帧 给出，同样只是**当前实测值**，不是承诺。

### 订阅 audio

`subscribe` 是整体替换语义（见「订阅」一节），所以订阅音频时必须**一次带上全部需要的频道**：

```json
{"channels": ["media", "lyrics", "audio"]}
```

只发 `["audio"]` 会把 `media` 与 `lyrics` 顶掉。

> MediaIsland 自带的实例间消费客户端遵循同样的规则：它在**本机有可视化消费者
> 且服务端在 `server.hello` 里声明了 `audio` 能力**时订阅音频，每次都发全量频道列表
> 而非增量；需求消失即退订并发 `audio.play_stop`。
>
> 两个条件缺一不可，且代价并不对称：向未声明 `audio` 能力的服务端请求该频道，
> 由于整体替换语义，`media` 与 `lyrics` 会**一起被拒**——用户为了看频谱，连歌词
> 都会失去。故客户端在能力未知时一律不请求 `audio`，宁可没有频谱。

### 帧格式

定长头 34 字节，之后是变长 `trackToken` 与裸 PCM，全部小端：

```
偏移  长度  字段
0     2    magic = 0xA1 0x01
2     1    version = 1
3     1    flags              bit0: 静音帧  bit1: 曲目首帧
4     8    startPositionMs    i64  本块首采样对应的曲目位置
12    8    capturedAtMs       i64  采样时刻，发送端墙钟（Unix 毫秒）
20    8    serverTimeMs       i64  发送时刻，发送端墙钟（Unix 毫秒）
28    4    seq                u32  音频帧独立序号
32    2    trackTokenLen      u16  UTF-8 字节数
34    N    trackToken         UTF-8
34+N  ...  PCM                i16 交错
```

`trackToken` 变长置于末尾，使头部定长部分可按固定偏移读取。

magic 或 `version` 不匹配、长度不足头部要求时，接收端**丢弃该帧但不断开连接**——未知 magic
可能是未来版本的其他二进制帧类型，按「必须容忍未知」原则处理。

### 三个时间戳

- `startPositionMs` — 曲目轴上的位置，用于把音频与歌词对齐。
- `capturedAtMs` / `serverTimeMs` — 同一时钟内求差的一对值，用法与 §进度插值
  完全相同：`(serverTimeMs - capturedAtMs) + (本地当前时刻 - 本地收帧时刻)` 即
  该帧的总延迟。**不要**拿 `serverTimeMs` 与本地时钟直接相减。

#### capturedAtMs 的时钟轴是契约

上面的求差用法只依赖「两值同钟」，但 `capturedAtMs` 的**绝对轴**同样是协议契约：
它必须落在**发送端墙钟轴（Unix 毫秒）**上。跨机对齐把它作为目标出声时刻算式的
第一项（`capturedAtMs × 10⁴ + dMs × 10⁴ + 线上offset`，见「回程对时」一节），而
墙钟桥 W 建立的正是「发送端墙钟 → 发送端单调钟」的映射——发送端若拿单调时钟
读数填这个字段，求差用法不受影响、没有任何报错，但每个接收端都会把它当墙钟搬轴，
错出一个等于「墙钟与单调钟零点之差」的巨大常量，所有接收端的对齐安静地坏掉。

发送端填法的义务：采样时刻应由「当前墙钟 − 帧龄」合成，其中帧龄在**单调钟内**
求差测得（本仓实现：`当前墙钟 − (当前单调钟 − 帧的采集时刻单调钟读数)`）。
单调时钟只用于求帧龄这个差值，不得直接作为 `capturedAtMs` 的轴。
`serverTimeMs` 同轴：直接取发送那一刻的墙钟。

`seq` 独立于 JSON 事件的 `seq`，因两者队列独立、丢弃策略不同。

### trackToken 校验

与歌词同理：帧的 `trackToken` 与当前曲目不符时应丢弃，避免切歌后把上一首的音频
配到新曲目上。

### 控制指令

| 类型 | 说明 |
|------|------|
| `audio.play_start` | 请求开始推送音频 |
| `audio.play_stop` | 停止推送 |

均需先认证。服务端回 `ok`，携带相同的 `id`，`payload.for` 为原请求的 `type`。

两者只表达**采集意愿**，不改变订阅状态——订阅仍由 `subscribe` / `unsubscribe` 管理。

服务端在**同时满足**以下条件时才采集：该连接已认证、已订阅 `audio`、且发过
`audio.play_start`。因此：

- 只 `subscribe` 不 `play_start`：不采集。
- 只 `play_start` 不订阅 `audio`：仍回 `ok`（意愿已记下），但不采集——先发
  `play_start` 再 `subscribe` 是合法顺序，届时采集自动开始。
- 退订 `audio` 或重发不含 `audio` 的 `subscribe`（整体替换语义）：采集需求随之消失。
- **连接断开**：该连接的意愿自动撤销，无需也无法补发 `play_stop`。最后一个有意愿的
  连接消失后服务端停止采集并释放音频设备。

> 服务端按「当前所有连接的状态」重算采集需求，而非对 start/stop 计数。
> 故客户端进程被杀这类不发关闭握手的情形同样能正确收敛。

若服务端的原生音频库不可用（缺失或 ABI 不匹配），`audio.play_start` 仍回 `ok`
但不会有帧推出；`media`、`lyrics`、转发与封面等其余能力不受影响。
`capabilities` 声明的是**协议支持**，不是运行时可用性——两者刻意分离，
否则一次设备故障会让客户端误以为对端根本不懂这个协议。

### 注入（转发链路）

音频的注入**没有独立消息类型**。一条连接上入站的音频二进制帧即是注入，格式与推送
完全相同——方向已由「谁发的」确定，无需再用类型字段区分。这与 `media.inject` /
`lyrics.inject` 需要独立类型不同：那两者的入站与出站载荷形状本就不一样。

转发时**原样透传**帧，不重组、不改写时间戳。`media.inject` 需要 `positionAgeMs`
来补偿每一跳的耗时，音频帧则因头部自带 `capturedAtMs` / `serverTimeMs` 而不需要——
接收端用同一个公式即可算出累计延迟。

「不改写」是可依赖的契约而非实现细节：多跳之后，`capturedAtMs` / `serverTimeMs` /
`seq` 仍然是**最初采集端**的读数，而不是最后一跳中继的。故链末的客户端算出的是
端到端延迟，而不是只覆盖最后一跳的延迟。中继若改写它们，最初那一跳的时间信息就没了，
且这种损失在报文里看不出来——数值依然合理，只是含义变小了。

### 背压

音频有独立于 JSON 帧的出站队列（8 帧，按当前实测帧长约 80ms），**满时丢最旧，不关闭连接**。

这与 §出站队列与背压 描述的 JSON 队列策略相反，是刻意的：可视化只关心「现在在
响什么」，积压的历史帧已经过期；播放侧的连续性由接收端缓冲负责。

队列按**帧数**而非时长计量，故其实际时长随设备帧长变化。这不影响正确性：
丢最旧的前提下，队列深度决定的是「发送暂时卡顿时保留多少最新帧」，
而过期帧对可视化本就无价值。

因此音频 `seq` 跳号是正常的背压结果，不代表故障。

## 封面

有两条获取途径，任选其一。已经建立 WebSocket 连接的客户端**建议走 WebSocket**：无需把 Token 放进 URL，也不必为一张图另开一条 TCP 连接。

### 途径一：WebSocket（推荐）

#### `thumbnail.get`（客户端→服务端）

认证后可发送，不要求订阅任何频道。

```json
{
  "type": "thumbnail.get",
  "id": "th1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "trackToken": "abc123def"
  }
}
```

`payload.trackToken` 可选。填入时服务端会与当前有效曲目比对，不一致则返回空数据——这可以防止切歌后把上一首的封面配到新曲目上。省略则不做校验。

服务端回复 `thumbnail`，携带相同的 `id`：

```json
{
  "type": "thumbnail",
  "id": "th1",
  "v": 1,
  "ts": 1710000000000,
  "payload": {
    "trackToken": "abc123def",
    "mimeType": "image/png",
    "dataBase64": "iVBORw0KGgo..."
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `trackToken` | string? | 本次封面所属曲目的标识；无媒体时为 null |
| `mimeType` | string? | 有数据时为 MIME 类型，否则为 null |
| `dataBase64` | string? | base64 编码的图片数据；无可用封面时为 null |

`dataBase64` 为 null 的三种情形——曲目无封面、封面超过 1 MiB、`trackToken` 与当前曲目失配——**都不是错误**，客户端按「当前无可用封面」处理即可。此时 `trackToken` 仍会返回当前值，客户端可据此判断是否需要重新请求。

无任何媒体会话时返回 `error` + `no_session`。

浏览器端可直接拼成 data URL：

```js
img.src = `data:${p.mimeType};base64,${p.dataBase64}`;
```

### 途径二：HTTP 端点

```
GET /v1/thumbnail?token=<token>&t=<trackToken>
```

适用于无法维持 WebSocket 连接的场景（例如把 URL 直接填进 OBS 图像源）。

- 与 WebSocket 共用同一 Token 与同一监听端口
- `t` 参数可选，用于缓存失效，服务端只做存在性比对
- 成功返回 `image/png`，`Cache-Control: no-store`
- 401: Token 不匹配
- 404: 无媒体、无封面或 `t` 已过期

> **安全提示**: 此 URL 含 Token，不应写入日志或分享。浏览器 `<img>` 无法携带自定义请求头，这是该端点只能用 query 传 Token 的原因；能用 WebSocket 时优先用 WebSocket。

封面上限为 **1 MiB**，超限时两条途径都按「无封面」处理。

## 错误码

| 错误码 | 说明 | 是否关闭连接 |
|--------|------|-------------|
| `unauthorized` | 未认证或 Token 错误 | 是 (1008) |
| `bad_request` | 请求格式错误 | 否 |
| `protocol_error` | 协议级错误 | 是 |
| `internal` | 服务端内部错误 | 否 |
| `rate_limited` | 出站队列溢出 | 是 (1011) |
| `not_supported` | 功能未启用 | 否 |
| `no_session` | 无活跃媒体会话 | 否 |

### 服务端主动关闭

服务停止（插件禁用、设置变更触发监听器重建、宿主退出）时，服务端会先发
**1001 GoingAway** 再断开，不携带 `error` 消息。

客户端据此区分「服务端正常下线」与「网络故障」：收到 1001 表示对端有序停止，
通常应当继续重连等待其恢复；而 1006（异常断开）则可能是网络问题。
注意 Token 变更同样走这条路径——重连时需要使用新 Token。

## 出站队列与背压

- 每个客户端有独立的 64 槽位出站队列
- 队列满时只挤掉**最旧的可丢帧**（`media.updated`，客户端有插值兜底）；
  队头恰好是歌词或控制帧时不会被误丢
- `lyrics.updated` 与控制帧不可丢。队列满且无可丢帧可牺牲时，以 `rate_limited` + 1011 关闭该客户端
- 单帧发送超时 5 秒，超时视同该会话故障并断开
- 一个慢客户端**不影响**其他客户端的推送

因此 `media.updated` 的 `seq` 可能跳号，这是正常的背压结果，不是消息丢失故障；
`lyrics.updated` 的 `seq` 不会因背压跳号。

## 序列号 (`seq`)

每个事件携带单调递增的 `seq`（从 1 开始）。客户端可用于:

- 检测消息乱序（丢弃 `seq` 不大于已处理值的消息）
- 检测消息丢失（`seq` 跳变，通常是队列丢弃了可丢帧）

> **重要**: `seq` 在服务端重建监听器后从 0 重新开始。客户端必须在 `server.hello` 的
> `sessionEpoch` 变化时重置已处理水位，否则重启后会永久停止更新。

## 最小客户端示例

```python
import asyncio, websockets, json

async def main():
    async with websockets.connect("ws://127.0.0.1:21757/v1/ws") as ws:
        await ws.recv()  # server.hello
        await ws.send(json.dumps({"type":"auth","id":"a1","v":1,"ts":0,"payload":{"token":"YOUR_TOKEN"}}))
        await ws.recv()  # auth_ok
        await ws.send(json.dumps({"type":"subscribe","id":"s1","v":1,"ts":0,"payload":{"channels":["media","lyrics"]}}))
        await ws.recv()  # subscribe_ok
        while True:
            msg = json.loads(await ws.recv())
            if msg.get("name") == "media.updated":
                p = msg["payload"]
                print(f"{p.get('title')} - {p.get('artist')} [{p.get('playbackState')}]")

asyncio.run(main())
```
